# وكيل العروض (Offers Agent) — النسخة الأولى

## ماذا يفعل؟

عندما يطلب العميل عرضًا رسميًا، ينشئ وكيل العروض **مسودة عرض فقط**:

1. يسعّر الطلب عبر وكيل التسعير الحالي (`priceRequirements` ← محرك التسعير الحتمي).
   لا توجد أي خانة سعر في مدخلات الوكيل، فلا يستطيع ذكاء اصطناعي اختراع سعر.
2. ينشئ العرض على الجداول الموجودة `offers` / `offer_items` — لا جداول جديدة.
3. يرقّم العرض بصيغة `OFOQ-2026-001` (فريد، متسلسل لكل سنة).
4. يرفق بنود الخدمات وأسعارها بالدولار (USD)، وشروط الخدمة ثنائية اللغة،
   وتاريخ انتهاء (14 يومًا افتراضيًا).

## دورة الحياة والصلاحيات

```
DRAFT ──(موافقة المالك/الشريك: approveAndSendOffer)──▶ SENT ──(قبول العميل: approveOffer)──▶ APPROVED (+ فاتورة)
                                                          └──(رفض العميل: rejectOffer)──▶ REJECTED
SENT منتهي الصلاحية عند القبول ──▶ EXPIRED
```

- **الإنشاء:** `createFormalOfferDraft` في `src/lib/agents/specialists/offers.agent.ts` — دائمًا `DRAFT`، لا يُرسل أبدًا.
- **مراجعة/تعديل المالك:** `updateDraftOffer` (صلاحية `offers.manage`، مسودات فقط).
  تغيير البنود يُعاد تسعيره من كتالوج الخدمات عبر محرك التسعير — لا أسعار حرّة.
- **الإرسال:** `approveAndSendOffer` هي الطريق الوحيد من `DRAFT` إلى `SENT`
  (المالك/الشريك فقط). الإرسال في هذه. النسخة يعني نشر العرض للعميل داخل المنصة؛
  لا يُرسل أي بريد حقيقي.
- **قبول/رفض العميل:** `approveOffer` / `rejectOffer` — العميل صاحب العرض فقط،
  وحالة `SENT` غير منتهية فقط. القبول يُصدر فاتورة عبر خدمة الفوترة الموجودة.
- وكيل المقترحات القديم (`proposal_writer`) لم يعد يُرسل تلقائيًا؛ كل عروضه مسودات.

## حماية البيانات

- عرض العميل (`toClientOfferView` / `getClientOfferView`) لا يحتوي التكلفة
  الداخلية ولا الهامش ولا الملاحظات الداخلية.
- العميل لا يرى المسودات ولا عروض غيره (`getOfferForActor` + `assertCustomerAccess`).
- كل انتقال حالة يُسجَّل في سجل النشاط، وتشغيل الوكيل يُسجَّل عبر `runAgent`.

## الربط بالواجهات (API)

| الإجراء | المسار | من يستطيع |
|---|---|---|
| طلب عرض رسمي (ينشئ مسودة) | `POST /api/offers` | العميل (أو الموظف مع `customerId`) |
| قائمة العروض | `GET /api/offers` | الموظف كاملة / العميل: عروضه المنشورة فقط وبالعرض الآمن |
| عرض واحد | `GET /api/offers/[id]` | الموظف كاملاً / العميل صاحب العرض (لا مسودات) |
| تعديل مسودة | `PATCH /api/offers/[id]` | المالك/الشريك فقط، مسودة فقط |
| اعتماد المالك والإرسال | `POST /api/offers/[id]/send` | المالك/الشريك فقط |
| قبول/رفض العميل النهائي | `POST /api/offers/[id]/decision` | العميل صاحب العرض فقط |

- لوحة العميل: نموذج «طلب عرض رسمي» في قسم العروض، وأزرار قبول/رفض تظهر
  للعروض بحالة `SENT` فقط، مع البنود والأسعار وتاريخ الصلاحية والشروط.
- لوحة الإدارة: في قسم الطلبات، للمسودات تعديل أيام الصلاحية وزر
  «اعتماد وإرسال للعميل». موافقة المالك (إرسال) وقبول العميل قراران منفصلان
  تمامًا، ولا يستطيع أيٌّ منهما القيام بدور الآخر (يُختبر ذلك عبر HTTP).

## ماذا يحدث عند قبول العميل؟ (سلوك مالي دقيق)

قبول العرض (`approveOffer`) يقوم تلقائيًا بما يلي — ولا شيء غيره:

1. يحوّل العرض إلى `APPROVED` ويسجّل وقت القبول.
2. **ينشئ فاتورة** عبر خدمة الفوترة الموجودة (`createInvoiceFromOffer`)
   بحالة `ISSUED` برقم `INV-<year>-NNNN` وتاريخ استحقاق (7 أيام افتراضيًا).
3. **يرسل إشعار فاتورة بالبريد** للعميل عبر `notifyClientInvoice` ←
   `sendEmail`: إذا كان مزوّد البريد (Resend) مهيّأً في البيئة فهذا بريد
   حقيقي تلقائي عند القبول؛ وإن لم يكن مهيّأً يُكتب في سجل الخادم فقط.
   (لم يُشغَّل أي بريد حقيقي أثناء التطوير/الاختبارات.)
4. إن كان العرض مرتبطًا بمشروع، يحوّل المشروع إلى `AWAITING_PAYMENT`.

لا يوجد أي خصم أو دفع أو تحصيل تلقائي، ولا إنشاء اشتراك/حملة. الدفع يبقى
يدويًا كما كان. إصدار الفاتورة+الإشعار سلوك موجود أصلًا في مسار القبول،
ويجب أن يعرفه المالك قبل تفعيل قبول العملاء في الإنتاج.
